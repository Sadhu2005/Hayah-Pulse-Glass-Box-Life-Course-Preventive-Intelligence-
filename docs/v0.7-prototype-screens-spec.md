## 1. Goal

Build **three interactive screens** that consume synthetic cohort + engine outputs and demonstrate Outputs A/B/C from [v0.4-outputs-and-ux.md](./v0.4-outputs-and-ux.md).

**Stack:** React + Vite + Tailwind CSS  
**Shared chrome:** App nav with three tabs + footer `Synthetic demo data — not real patients`

## 2. Screen map

| Screen | Route | Output |
| --- | --- | --- |
| Clinician Portal | `/clinician` | Output A — Reason-for-Flag |

## 3. Screen 1 — Clinician Portal

### Components

| Component | Responsibility |
| --- | --- |
| `PatientPicker` | Dropdown/search over 500 synthetic residents |
| `RiskTierBadge` | high / medium / low / baseline_onboarding |
| `ConfidenceBadge` | High / Medium / Low confidence copy |
| `PathwayRecommendation` | Router string |
| `ReasonList` | Top 3–5 auditable drivers |
| `HouseholdCareGapAlert` | Shows if HH bundle hint exists |
| `ClinicalFirewallNotice` | Mandatory disclaimer |
| `ApprovePreventiveOrderButton` | One-click; sets local `orderApproved=true` toast |

### Acceptance criteria

- [ ] User can select any synthetic patient
- [ ] Risk tier, confidence badge, pathway, and top reasons render from engine output
- [ ] Household care-gap alert appears when `household_bundle_hint` is present
- [ ] Clinical firewall notice is always visible
- [ ] Approve button produces a visible confirmation (no real order API)
- [ ] Sparse-record patients show Baseline Onboarding, not a high-risk alert

---

## 4. Screen 2 — Citizen Mobile Simulator

Visual frame should feel like a phone / WhatsApp-style preview (not a desktop form dump).

### Components

| Component | Responsibility |
| --- | --- |
| `LanguageToggle` | Arabic ↔ English (minimum) |
| `WhyYouSection` | Plain-language invitation reason |
| `DataUsedLedger` | Authorized sources + explicit not-used list |
| `CareModalitySelector` | Clinic / Telehealth / Home Visit |
| `HouseholdBundleOption` | Optional same-visit adult IFHAS offer |
| `OptOutToggle` | Manage predictive outreach preferences |
| `MessagePreview` | LLM or template-rendered bilingual body |

### Acceptance criteria

- [ ] Message reflects the **selected** patient/parent context from Screen 1
- [ ] Arabic and English content both available
- [ ] Why You + Data Used + Not Accessed are all visible
- [ ] Care modality selection is interactive (local state)
- [ ] Opt-out toggle works without removing standard-care disclaimer copy
- [ ] Copy never claims real clinical diagnosis

### LLM guardrails (if used)

- Prompt may only use fields from engine output + resident display fields.
- Forbidden: inventing diagnoses, medications, or unauthorized data sources.
- Fallback: deterministic bilingual templates if API key absent.

## 5. Screen 3 — Public Health & Fairness Monitor

### Components

| Component | Responsibility |
| --- | --- |
| `ConversionFunnel` | Flagged → Invited → Booked → Completed → Follow-up |
| `SegmentParityMatrix` | Rates by age band, sex, district, resident_segment |
| `SmallCellShieldDemo` | Live mask for cells with `n < 10` |
| `MetricCards` | Recommendation rate, FPR/FNR proxies, attendance |

### Synthetic funnel fields

If not present in raw cohort, derive/simulate in backend or frontend aggregation module:

- `flagged`, `invited`, `booked`, `completed`, `followup_resolved` (booleans or stage enum)

### Acceptance criteria

- [ ] Funnel renders for full cohort
- [ ] Parity matrix shows ≥2 segment dimensions
- [ ] Any cell with `n < 10` displays `<10 — Suppressed for Privacy` (not raw counts)
- [ ] Toggle or callout demonstrates suppression clearly for judges
- [ ] No resident-level PHI-like drilldown on this screen

---

## 6. Data loading

Prototype may:

1. Load static JSON from `data/synthetic/` via frontend public assets, **or**
2. Serve via a thin Python API (`FastAPI`) from `backend/`.

Prefer API if engine re-run is needed; static JSON is acceptable for demo freeze.
